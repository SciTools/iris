## Review Focus

Five things that no test in the suite exercises and that a person loading
published Zarr would meet in ordinary work. Each is pinned by a test in the
task named. All five were run against the GFS subset or against a store built
in `tmp_path` on 2026-10-26; none is speculative.

1. **A CRS variable a store references through `coordinates` rather than
   `grid_mapping`.** The NOAA GFS archive does this. Iris builds no coordinate
   system from it, so `cube.coord("latitude").coord_system` is `None` and
   `spatial_ref` arrives as a scalar auxiliary coordinate carrying `crs_wkt`.
   A user who sees a `crs_wkt` in the file and no coordinate system on the cube
   will read it as an Iris bug. → **Task 3, Step 1**:
   `test_the_crs_variable_arrives_as_a_coordinate_not_a_coordinate_system`,
   and **Task 7** raises the issue.
2. **An attribute whose name collides with an array property.** The published
   store gives `lead_time`, `expected_forecast_length` and
   `ingested_forecast_length` an attribute literally called `dtype`, holding
   `"timedelta64[us]"`. That is one of the six names the merge-back changelog
   records as having been silently shadowed on load, and the programme's fix
   for it has never been run against a store that actually contains one. →
   **Task 3, Step 1**: `test_an_attribute_named_dtype_does_not_shadow_the_dtype`.
3. **Replacing a store that already exists.** `test_save.py` pins that the
   default `mode="w-"` refuses an existing target, and that `mode="a"` adds to
   one. Nothing pins that `mode="w"` — the keyword §4.5 offers as the way back
   to replacement — actually replaces, so a script rerun over the same path,
   or an ASV timing function called a second time, rests on an untested
   promise. → **Task 3, Step 1**:
   `test_an_existing_store_is_replaced_under_mode_w`, and **Task 5, Step 1**,
   where `ZarrSave` depends on it.
4. **Reading a fixed-length unicode variable.** `<U` dtypes are tested on the
   write side in `test__encode.py` and
   `dataset/test_ZarrDataset__write.py`, and nowhere on the read side.
   [#6961](https://github.com/SciTools/iris/issues/6961) records that they are
   not strictly Zarr-supported, and published stores contain them. → **Task 4**,
   the whole task.
5. **A round trip that silently drops the source layout.** The GFS arrays are
   sharded `(1, 4, 120, 120)` over inner chunks `(1, 2, 40, 40)`; saved back,
   they are `chunks=(2, 8, 120, 120)` with no shards. Nothing promises
   otherwise, and nothing says so either, so a user round-tripping a real store
   loses its layout without being told. → **Task 3, Step 1**:
   `test_the_round_trip_does_not_keep_the_source_chunk_layout`.

  says a cut-down copy of the real store replaces it. Keeping it is the better
  trade: it needs no external data, so `test_load.py` keeps running where
  `iris-test-data` is absent, and the two are not redundant — the synthetic
  store is the more CF-conforming of the pair (F1). Task 3 corrects the
  docstring.

  claim has been inaccurate since 2019 and the clearest instance is not one of
  this pull request's (F16). A repository-wide licence statement is a SciTools
  decision; Task 7 raises it as an issue.
- **Any library behaviour change.** Every test this plan adds characterises
  what the branch already does. A test that fails is a defect to record and
  raise, not to fix here; fixing it would put a behaviour change in a pull
  request whose diff is otherwise tests and benchmarks.
- **A Zarr `TimeConstraint` or `STASHConstraint` benchmark.** Spec §5 names
  `ZarrSave` and `LoadAndRealise`. The others are about constraint handling,
  which is format-agnostic.
- **A Zarr `save_mesh` benchmark.** `iris.mesh.save_mesh` is netCDF-only
  (F10).
- **Preserving a source store's chunk and shard layout through a round trip.**
  Iris sizes chunks itself and nothing in §4.4 or §4.5 promises otherwise
  (F2). Task 3 pins the current answer; changing it is its own pull request.
- **The terms-of-art sweep.** PR 8.
- **Changelog fragments and closing keywords.** The merge-back owns both.

## 3. Findings that refine the spec

Numbered so that tasks can cite them. Each was checked against the code, the
published store, or this machine, on 2026-10-26.

**F1. The GFS sample loads clean, and does not exercise the grid-mapping
path.** `iris.load` on `~/iris-zarr-testdata/gfs_forecast_sample.zarr` returns
four cubes — `air_temperature`, `eastward_wind`, `northward_wind`,
`precipitation_flux` — with `LOAD_PROBLEMS.problems == []` and no warning.
The four data arrays name `spatial_ref` in `coordinates`, and none of them has
a `grid_mapping` attribute at all. So `spatial_ref` arrives as a scalar
auxiliary coordinate carrying `crs_wkt`, `semi_major_axis` and the rest, and
`cube.coord("latitude").coord_system` is `None`. Spec §7 says the subset keeps
"the scalar `spatial_ref` grid mapping", which is true of the variable and not
of the reference. The synthetic fixture in `integration/zarr/fixtures.py` gives
its data variable `grid_mapping: spatial_ref` and is therefore the more
CF-conforming of the two.

**F2. The GFS sample round-trips, losing `Conventions` and its chunk layout.**
Saving the loaded `air_temperature` cube and reloading it gives a cube equal in
every metadata field except the global `Conventions`, which the saver adds as
`CF-1.7`; the data compares equal. The source arrays are `chunks=(1, 2, 40,
40)` with `shards=(1, 4, 120, 120)`; the saved arrays are `chunks=(2, 8, 120,
120)` with `shards=None`. xarray opens the result and sees four data variables
and eight coordinates.

**F3. The whole sample is about a second's work.** 0.73 s to load four cubes,
0.38 s to save them. 1.4 MB, 35 files. No special handling is needed to keep
the suite fast.

**F4. The published store carries an attribute called `dtype`.** `lead_time`,
`expected_forecast_length` and `ingested_forecast_length` each hold
`dtype: "timedelta64[us]"`, producer bookkeeping that CF has no meaning for.
On the loaded cube, `coord.attributes["dtype"]` is `"timedelta64[us]"` while
`coord.dtype` is `float64`, and the two coexist. `dtype` is one of the six
names the merge-back changelog lists as having been silently shadowed on load,
so this is the fix meeting a store that contains the thing it was written for.

**F5. A fixed-length unicode variable loads, and nothing tests that it does.**
A `<U3` array written into a `tmp_path` store and named in a data variable's
`coordinates` comes back as a string auxiliary coordinate with its values
intact, on version 2 and version 3 alike. Every `<U` test in the suite is on
the write side — `test__encode.py` and
`dataset/test_ZarrDataset__write.py:593`.

**F6. Dropping the EOPF fixture costs one test.** Of what it was going to
cover, three are already covered by stores built in `tmp_path`: the raise when
a root group holds no data variables, at
`unit/fileformats/zarr/loader/test_load_cubes.py:135` and `:141`, written
against the EOPF shape and matching on `"measurements"`; the version 2
fill-value split, at `unit/fileformats/zarr/test__decode.py:118` and `:123`;
and nested JSON attributes, at
`unit/fileformats/zarr/dataset/test_ZarrDatasetVariable.py:226` and
`loader/test_load_cubes.py:192`. The one gap is F5, and Task 4 fills it. Spec
§6 also already provides for version 2 reading two ways that do not need a
published store: synthetic fixtures with `_ARRAY_DIMENSIONS` set by hand, and
the existing NCZarr `mode=xarray` save path.

**F7. Saving twice to the same Zarr target raises.** The second
`iris.save(cube, path)` raises `FileExistsError`: "Cannot create the Zarr store
'...': it already exists, and mode='w-' will not overwrite it." ASV calls a
timing function many times between `setup()` calls, so a `ZarrSave` that
mirrors `NetcdfSave` literally fails on its second call. `mode="w"` is what the
benchmark needs, and `mode="w"` does replace.

**F8. `create_um_files` tests for a file, and a store is a directory.** Its
reuse check is `save_path.is_file()`, which is `False` for a `.zarr` directory,
so the data would be regenerated on every run and `REUSE_DATA` would stop
meaning anything.

**F9. Zarr's compression keyword is `compressors`.** `compressors=None` gives a
codec tuple of `()`; `compressors="auto"` gives `ZstdCodec(level=0,
checksum=False)`. The netCDF branch of `_create_um_files` passes
`zlib=compress`, and the Zarr branch cannot: spec §4.5 forbids translating
netCDF keywords onto Zarr codecs, and the saver raises `TypeError` on `zlib`.

**F10. `iris.mesh.save_mesh` is netCDF-only.** It is defined in
`iris/fileformats/netcdf/saver.py`. A cube that *has* a mesh does save its mesh
to Zarr — checked on a 50-cubesphere, which round-tripped with its mesh intact
— but there is no standalone mesh entry point to benchmark.

**F11. Benchmarks run on this machine without nox.** `python
benchmarks/bm_runner.py trialrun "CubeCreation.time_create" "$(which python)"`
completed and reported timings, using `asv run --environment existing:`. It
needs `asv`, `nox`, an importable Iris, and — for anything `create_um_files`
builds — Mule, which `bm_runner` installs only when it builds the environment
itself.

**F12. §12.5 records the wrong path for the GFS artefact.** It says
`~/projects/iris-zarr-testdata/gfs_forecast_sample.zarr`. The store is at
`~/iris-zarr-testdata/gfs_forecast_sample.zarr`.

**F13. The test-data indexer descends into a store.** `getDataFilepaths` in
`indexing/generate_index.py` takes every file whose suffix is not in
`IGNORE_SUFFIXES` and hands each to `iris.load`. A version 3 store contributes
one `zarr.json` per array plus every chunk object, so the GFS subset alone
would add about 35 entries to INDEX.md, nearly all of them error blocks.

**F14. `IRIS_TEST_DATA_VERSION` is pinned in two workflow files.**
`.github/workflows/ci-tests.yml` at `2.30`, with a comment pointing at
`.github/workflows/benchmarks_run.yml`, which pins the same value. Both fetch
`https://github.com/SciTools/iris-test-data/archive/v${VERSION}.zip`, so
neither can be bumped before the companion pull request merges and the version
tag exists.

**F15. The local test-data checkout is behind CI.** `version.txt` reads 2.29;
CI pins 2.30. Pull before adding anything.

**F16. `iris-test-data` already redistributes third-party data under a
copyleft licence.** `test_data/NetCDF/volcello/volcello_Ofx_CESM2_deforest-globe_r1i1p1f1_gn.nc`
carries a `license` global attribute naming Creative Commons
Attribution-ShareAlike 4.0 International, and NCAR as the producer. It was
added in `1696ac3` on 2019-09-25, is 8.4 MB on the full published grid with its
CMIP6 `tracking_id` intact, and looks like the published file redistributed
unchanged. `README.rst` claims British Crown copyright over the whole
repository and offers it all under the Open Government Licence; it has been
inaccurate since that file landed, and the GFS subset's CC BY 4.0 is a lighter
obligation than the one already there. So the GFS contribution records its own
provenance and licence, and the repository-wide claim is raised as an issue
rather than edited here.
