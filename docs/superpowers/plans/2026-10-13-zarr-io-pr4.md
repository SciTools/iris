**Created:** 2026-10-13

Claims marked **[verified]** were checked by running code in the `iris-dev`
environment against zarr-python 3.4.1 while this plan was written; everything
else is read from source or from the spec.

**Goal:** Make `iris.load("store.zarr")` and
`iris.load("s3://bucket/store.zarr")` return cubes from a native Zarr version 2
or version 3 store, by implementing the `CFDataset` interface over zarr-python
and teaching Iris's load chain that a target can be a directory or a URL rather
than a seekable file.

**Architecture:** `iris/fileformats/zarr/_dataset.py` implements `CFDataset` and
`CFDatasetVariable` over a `zarr.Group` and its `zarr.Array`s, which is all the
CF layer from PR 2 and PR 3 needs in order to classify variables and build
cubes. There is no data proxy: `zarr.Array` is picklable, so `read_data` hands
it straight to `as_lazy_data` and adds CF decoding — masking, `valid_range`,
`scale_factor`/`add_offset` — as explicit `map_blocks` layers over the raw
array, implemented as pure functions in `_decode.py`. `iris/fileformats/zarr/
loader.py` is a thin `load_cubes` that opens a `ZarrDataset`, hands it to
`CFReader`, and runs the same `_load_cube` loop the netCDF loader runs.
`iris.io.load_stores` is the new entry point for a target that is not a file,
and a `ZarrStore` file element lets `FORMAT_AGENT` recognise one.

**Tech Stack:** Python 3.12–3.14, zarr-python ≥3.0.8, NumPy, Dask, pytest +
pytest-xdist, pre-commit (ruff, numpydoc, mypy, sort-all), `abc.ABC`,
`collections.abc.MutableMapping`.

**Spec:** [`../specs/2026-09-21-zarr-io-design.md`](../specs/2026-09-21-zarr-io-design.md)
— §2.4 lists the Zarr facts that shape the design, §3 the constraints agreed
before design, §4.1 the module layout, §4.2 the `CFDataset` interface, §4.4 the
whole of reading, §4.6 groups, §4.7 format detection and the load chain, §5's
fourth entry is this pull request, §6 the testing rules. The plan argues from
the spec; read both.

## Review Focus

Five failure modes the spec implies that **no task's own tests would otherwise
exercise**, most likely first. Each names the input or condition and the
behaviour a reasonable person expects; each has a test added to the task that
owns the code, written out in that task's own step style.

1. **A version 2 store's `_ARRAY_DIMENSIONS` attribute landing on the loaded
   cube.** It is how a version 2 store records dimension names, so under the
   §4.2 split it is a *property*, not a CF attribute — and every attribute a
   `CFVariable` does not consume reaches `cube.attributes`
   (`cf/loader.py::_add_unused_attributes`). Nothing in `_CF_ATTRS` excludes
   it, so unless `ZarrDatasetVariable.attributes` withholds it, every cube
   loaded from a version 2 store gains a stray `_ARRAY_DIMENSIONS` attribute
   and fails to compare equal to the same cube loaded from version 3. The user
   expects the two to be indistinguishable. → **Task 3, Steps 9–10**.

2. **A store whose root group holds no arrays.** Spec §4.6 requires "a message
   that names the groups that do", and §7 records a real store in that shape —
   the ESA EOPF Sentinel-2 product, whose root holds only subgroups. The
   failure to defend against is not the message but its absence: an empty
   `CubeList` returned silently from `iris.load` of a store that plainly
   contains data is the worst available answer, and the one that falls out of
   writing the loop without thinking about it. → **Task 9, Steps 7–8**.

3. **`iris.load("data/*")` matching a mix of `.nc` files and `.zarr`
   directories.** Spec §4.7 states the requirement and names the consequence —
   the file-or-store decision has to happen after glob expansion and before
   format dispatch. The quiet failure is partial: `_generate_cubes` partitions
   what `expand_filespecs` returns, so a bug that mis-partitions raises
   `IsADirectoryError` from `load_files` for the stores while the netCDF files
   load fine, and a user who did not expect the glob to match a store reads it
   as an Iris bug. → **Task 11, Steps 11–12**.

4. **A `scale_factor` or `add_offset` that changes the result dtype.**
   `cf/loader.py::_get_actual_dtype` computes the post-unpacking dtype and the
   netCDF path gets the arithmetic itself from netCDF4. On the Zarr path Iris
   does the arithmetic, in `_decode.py`, so the dask array's declared dtype and
   what the decode layer actually produces are two separately-written
   statements that must agree. When they disagree dask does not complain: the
   graph is built, and the mismatch surfaces later as a wrong dtype on the
   cube, or as a `ValueError` from a downstream operation. A `uint16` band with
   `scale_factor = 0.0001` — the EOPF reflectance case in spec §7 — must give a
   `float64` cube whose lazy and realised dtypes match. → **Task 6, Steps 11–12**.

5. **A `zarr` that is installed but too old, or not installed at all.** Spec §3
   requires "a clear `ImportError`" and §6 requires that "Iris without zarr
   installed must show no new failures". Two distinct paths reach a user here —
   `iris.load` of a `.zarr` target, and `import iris.fileformats.zarr` — and the
   second is the one that breaks the first rule by accident, because
   `iris.fileformats.__init__` imports every format module it registers. If the
   Zarr import is not deferred, installing Iris without zarr stops `import iris`
   working at all. → **Task 1, Steps 5–8**.

## 2. Findings that refine the spec

Checked while writing this plan. Each is either a correction the implementer
would otherwise hit as a failing test, or an answer the spec asked for.

**F1 — `zarr.Array` has no `dimension_names` property.** Version 3 names live
at `Array.metadata.dimension_names`; `ArrayV2Metadata` has no such attribute
and raises `AttributeError`, not the `ValueError` spec §2.4 quotes
**[verified]**. So `ZarrDatasetVariable.dimensions` must branch on
`metadata.zarr_format` and read `attrs["_ARRAY_DIMENSIONS"]` on version 2 —
never `try: … except ValueError`.

**F2 — zarr-python rejects a wrong-length `dimension_names` at creation.**
`create_array(..., shape=(2, 2), dimension_names=("y",))` raises
``ValueError: `dimension_names` and `shape` need to have the same number of
dimensions`` **[verified]**. Spec §4.4 requires Iris to warn and load
anonymously for such a store, so the fixture for that test cannot be built
through the zarr-python API — it has to write `zarr.json` by hand.

**F3 — spec §12.3 Q2 is answered: `<U7` reads fine.** A fixed-length unicode
array creates, writes and reads back with its dtype intact on **both** version
2 and version 3 **[verified]**: `dtype('<U7')`, values
`array(['alpha', 'beta'], dtype='<U7')`. #6961's note that these are "not
strictly Zarr-supported" describes the specification, not zarr-python's
behaviour, and no special handling is needed. Close Q2 in spec §12.3 with this
answer.

**F4 — `Array.metadata.to_dict()` is JSON-serialisable as it stands.** No
`default=` fallback is needed, on either version **[verified]**. The version 3
key set is `attributes, chunk_grid, chunk_key_encoding, codecs, data_type,
dimension_names, fill_value, node_type, shape, storage_transformers,
zarr_format`; version 2's is `attributes, chunks, compressor,
dimension_separator, dtype, fill_value, filters, order, shape, zarr_format`.
A small array's key is ~460–520 characters, matching spec §4.4's estimate.

**F5 — zarr-python copies a store when it opens it read-only.** `WrapperStore`
implements `with_read_only` by constructing a new instance through
`_with_store`, so after `zarr.open_group(store=my_wrapper, mode="r")` the
array's store **is not** `my_wrapper` **[verified]**. An instrumented store
that counts bytes must therefore keep its tally in an object the copy shares,
and override `_with_store` to pass it on. A counter stored on the instance
reads zero and the test passes vacuously.

**F6 — the sharding read-unit result reproduces, but not its byte counts.** On
`shape=(1024,)`, `chunks=(8,)`, `shards=(1024,)` int32, reading the first eight
values **[verified]**: inner-chunk dask blocks fetch 2,052 bytes with or
without a decode layer; shard-sized blocks fetch 2,052 without one and **7,300
with** one. The shape of spec §4.4's table holds exactly — a `map_blocks` layer
defeats slice pushdown, so a shard-sized block materialises the whole shard —
but the absolute numbers differ from the spec's 2,084 / 6,148. They are
zarr-version-dependent. **The test compares its own two measurements; it must
not pin a literal byte count.**

**F7 — `_optimum_chunksize` sub-chunks a large store chunk, exactly as spec
§4.4 says.** `chunks=(8000, 8000)`, `shape=(16000, 16000)`, `f8` gives
`(2000, 8000)`; `chunks=(6000, 6000)`, `shape=(6000, 6000)`, `f8` gives
`(2000, 6000)` **[verified]**. Both are the real regression cases for the
alignment guard, and neither needs a store to reproduce.

**F8 — the errors zarr-python raises for the targets Iris will meet**
**[verified]**:

| target | exception |
|---|---|
| a path that does not exist | `FileNotFoundError` |
| a directory that is not a store | `zarr.errors.GroupNotFoundError` |
| `group=` naming a group that is not there | `zarr.errors.GroupNotFoundError` |
| `s3://…` with no s3fs installed | `ImportError: Install s3fs to access S3` |

The last is why spec §3's "Iris adds no dependency and handles no credentials"
costs nothing to honour: zarr-python's own message already tells the user what
to install.

**F9 — a read-mode `zarr.Array` refuses attribute writes** with
`ValueError: store was opened in read-only mode and does not support writing`
**[verified]**. `CFVariable` copies `data.attributes` into a plain `dict` at
construction (`cf/_variables.py::CFVariable.__init__`), so loading never writes
through — but `ZarrDatasetVariable.attributes` must still be a `MutableMapping`
to satisfy the interface, and its `__setitem__` will raise that `ValueError`
from zarr-python on a read-mode store. That is the right answer and needs no
wrapping.

**F10 — the shared `CFDataset` contract has to be split in two.**
`lib/iris/tests/unit/fileformats/cf/dataset/contract.py` holds one class whose
`writable` and `reopen` fixtures drive `populate()` through `create_dimension`,
`create_variable`, `__setitem__` and `write_handle`. Spec §5 puts the Zarr
write path in PR 6, so the whole write half is unrunnable here. Split
`CFDatasetContract` into `CFDatasetReadContract` and `CFDatasetWriteContract`;
`test_NetCDFDataset.py` inherits both and its coverage is unchanged; the new
Zarr test module inherits the read half, and PR 6 adds the other. Keeping one
class and skipping half of it would hide, behind a skip, the fact that an
implementation is incomplete — spec §6's whole argument for a shared body is
that divergence "fails loudly".

**F11 — `format` has to land here, not in PR 5.** Spec §5 assigns
`CFDataset.format` and `CFDataset.supports_dtype` to PR 5, but PR 4 merges
first and `ZarrDataset` cannot answer `ZARR_V2` versus `ZARR_V3` without it:
the version-aware masking split (§4.4) and the warnings this pull request
emits both need to name the format. `supports_dtype` is genuinely a saver
concern and stays in PR 5. **Add `format` here; record the move in spec §12.4
and amend §5's PR 4 and PR 5 entries.**

**F12 — `CFReader` cannot yet be handed an open `CFDataset`.**
`cf/_reader.py::CFReader.__init__` has two branches: a `str` opens a
`NetCDFDataset`, and anything else goes to `NetCDFDataset.from_existing`. A
`ZarrDataset` would be wrapped as a netCDF dataset and fail. PR 4 adds a third
branch that takes an already-open `CFDataset` and borrows it. Note that
`isinstance(file_source, CFDataset)` tests the **interface**, which is what
spec §4.2 requires generic code to do; the rule it forbids is testing an
implementation class.

**F13 — the marker files are where spec §4.7 says they are** **[verified]**. A
version 2 store's root directory holds `.zgroup` and `.zattrs`; a version 3
store's holds `zarr.json`. One `Path.is_file()` each.

**F14 — attribute values round-trip through `Array.attrs` untouched**, for a
nested object (`{'min': 1, 'max': 2}`), a numeric vector (`[1.0, 2.0]`) and
`float("nan")` **[verified]**. The read side of spec §4.4's nested-attribute
rule therefore needs no code at all: the value arrives as a `dict` or `list`
and is carried onto the cube. It needs a **test**, because "we do nothing" is
indistinguishable from "we never tried it".

**F15 — `Group.arrays()` yields only that group's own arrays**, and
`Group.group_keys()` lists its subgroups **[verified]**. Together they are
exactly spec §4.6: one group per call, and a root group with no arrays can name
the groups that have them.

**F16 — the `(name, size)` change does not have to reach
`_nc_load_rules/helpers.py`.** Four sites there match dimensions by name —
`helpers.py` lines near `build_auxiliary_coordinate`,
`build_dimension_coordinate`, `_add_cell_measures` and
`_add_ancillary_variables` — and `None in (None, "x")` is `True`, so an
anonymous dimension reaching them would attach a coordinate to the wrong cube
dimension. It cannot reach them: `CFReader._build_cf_groups` drops any variable
whose `spans` is `False` and promotes it to a data variable of its own, and
under the new rule a variable with any anonymous dimension spans nothing.
Dimension coordinates are safe for a second reason — `CFCoordinateVariable`
identifies on `nc_var_name in nc_var.dimensions`, which no anonymous dimension
satisfies. **Task 7 pins both claims with tests** rather than leaving them as
prose; without them this finding is the kind of comment that goes stale
unnoticed.

**F17 — `_CF_ATTRS_IGNORE` already covers the four attributes Iris consumes.**
`cf/_variables.py` seeds attribute tracking with
`{"_FillValue", "add_offset", "missing_value", "scale_factor"}`, described as
"handled by the netCDF4 module". On the Zarr path they are handled by
`zarr/_decode.py` instead, so the seeding stays correct and needs no change —
but the comment naming netCDF4 does, and `valid_min`/`valid_max`/`valid_range`
are deliberately **not** in that set, so they reach the cube on both paths.

### Sequencing, and why it is this way

The order is: make a Zarr store answerable as a `CFDataset`, then make the CF
layer able to hold one, then make Iris able to find one.

1. **Tasks 1–6 build `ZarrDataset` bottom-up** and are testable without any of
   Iris's loading machinery. Each one ends with a store built in `tmp_path` and
   questions asked of it directly.
2. **Tasks 7–8 are the two changes to generic code.** They are separated from
   the Zarr work because they are the only parts a netCDF-only reviewer has to
   check, and because `spans` is the one place in this pull request where a
   mistake silently changes what loads from an existing netCDF file.
3. **Task 9 is the loader**, which can only be written once 1–8 exist.
4. **Tasks 10–11 are the load chain**, which is independent of everything above
   and could be reviewed by someone who knows nothing about Zarr. They come
   last among the code tasks because until Task 9 exists there is nothing for
   the chain to dispatch *to*.
5. **Tasks 12–14** are integration, documentation and the pull request.

The dependency that matters in the other direction is **PR 3**. This plan calls
`CFDatasetVariable.read_data`, `iris.fileformats.cf.loader._get_actual_dtype`,
`_LAZYVAR_MIN_BYTES` and `as_lazy_data(..., cache_key=...)`, none of which exist
until [#7316](https://github.com/SciTools/iris/pull/7316) merges. If this branch
is cut before then, rebase onto `brownfield` once it has merged and re-run
Task 6 and Task 9's tests before trusting anything.

Three points about this shape are worth stating once, here, rather than
repeating in every task.

**`fill_value` means different things on the two backends, deliberately.**
`NetCDFDatasetVariable.fill_value` returns the `_FillValue` *attribute*;
`ZarrDatasetVariable.fill_value` returns `Array.fill_value`, the *storage*
field. On netCDF the two coincide. On Zarr they are different things (spec
§4.4), and conflating them masks every valid zero in an array that never
declared a sentinel. Nothing generic reads `fill_value` to decide masking —
`zarr/_decode.py::decode_parameters` does, and it reads the CF attributes
first.

**`encoding` is readable and never interpreted.** Generic code may print it,
record it, or hand it back to a user; it must not branch on a key. Its keys are
the backend's own spelling: `chunks`, `shards`, `codecs`, `zarr_format` for
Zarr; `chunksizes`, `zlib`, `complevel` for netCDF. `chunking` is the typed,
guaranteed member that the chunk calculation reads (spec §4.2).

**`cache_key` is a member of `ZarrDatasetVariable`, not of the interface.**
`read_data` is the only caller and both implementations build their own key —
netCDF from `repr(proxy)`, Zarr from the metadata document. Putting it on the
ABC would add a member no generic code reads, which is the indirection
`lib/iris/AGENTS.md` bans for a single caller.
