**Goal:** Make `iris.save(cubes, "out.zarr")` write a CF-conforming Zarr version 3 store, by adding a write path to the `ZarrDataset` PR 4 built and a `Saver` subclassing the `CFSaver` PR 5 extracted.

**Architecture:** PR 5 left `cf/saver.py` holding every format-agnostic part of saving a cube — dimension naming, coordinate, bounds, mesh, cell-measure and grid-mapping variables, attribute compliance, lazy write collection — driven through the `CFDataset` interface and four hooks. PR 4 left `zarr/_dataset.py` holding a read-only `ZarrDataset` whose write members raise `NotImplementedError`. This plan fills in those members, adds a fifth hook for grid mappings so that nothing in generic code reaches for a netCDF4 object, and adds `zarr/saver.py`: a `Saver` that opens a store, a `save()` that takes Zarr's own storage vocabulary, and a `delayed_completion()` that returns a real `Delayed` owning the final metadata consolidation.

**Tech Stack:** Python 3.12–3.14, zarr-python ≥3.0.8, NumPy, Dask, xarray (test-only, for cross-reader conformance), pytest + pytest-mock, pre-commit (ruff, numpydoc, mypy, sort-all, and the repository's local hooks), Sphinx.

## 2. Git strategy: a branch over two unmerged pull requests

PR 6 needs both of its predecessors in one tree. It edits `zarr/_dataset.py`,
which exists only on PR 4, and it subclasses `CFSaver`, which exists only on
PR 5. Neither has merged.

So `zarr-io-pr-4-5-base` carries a merge of the two, and `zarr-io-pr-6`
branches from it. The merge commit, `52c478bf9`, resolved five conflicts and
recorded two things neither branch could have had on its own; read it before
starting, because one of them is a gap that will reappear:

> `ZarrDataset.supports_dtype`, the abstract method PR 5 adds to `CFDataset`
> after PR 4 wrote `ZarrDataset`. Both Zarr versions hold every NumPy numeric
> dtype, so it answers `True`. **Whichever of PR 4 and PR 5 rebases second must
> carry this**, or `ZarrDataset` stays abstract and every Zarr test errors.

That method is therefore *not* part of PR 6's diff, even though PR 6's branch
contains it. The same goes for every other line of the merge commit.

**When PR 4 and PR 5 have both landed in `brownfield`:**

```bash
git fetch upstream brownfield
git rebase --onto upstream/brownfield zarr-io-pr-4-5-base zarr-io-pr-6
```

That replays PR 6's own commits and drops the merge, which is why the merge is
a separate branch rather than the first commit of this one. Expect conflicts
only where review changed PR 4's `ZarrDataset` or PR 5's `CFSaver` hooks under
this work.

**Opening the pull request before that rebase is possible** means GitHub would
show PR 4's and PR 5's diffs inside PR 6. Open it as a draft against
`brownfield` only once at least one predecessor has landed, or open it against
whichever predecessor branch is still outstanding and retarget later. The
pull-request body says which it is.

## 3. Findings that refine the spec

Numbered so that tasks can cite them. Each is something checked against the
code or against zarr-python 3.4.1 and xarray 2026.9.0, not something the spec
already says.

**F1. The base is green, and the suite is the proof.** `11188 passed, 59
skipped` across `lib/iris/tests/unit` and `lib/iris/tests/integration` on
`52c478bf9`. Any failure outside the files a task touches is a rebase artefact,
not a bug this plan introduced.

**F2. Grid mappings need a fifth hook, and the body of the method does not
change.** `CFSaver._add_grid_mapping_to_dataset` binds
`grid_variable = cf_var_grid.variable` and then makes **63** plain attribute
assignments to it. `.variable` is netCDF4's own object; `ZarrDatasetVariable`
has no such member, so a Zarr save of any cube with a coord system raises
`AttributeError` today. Q8 refuses to regularise the encoding in this
programme, because routing those 63 through `.attributes` changes what lands in
a netCDF file — `crs_wkt` is `NC_STRING` while `grid_mapping_name` is
`NC_CHAR`. The resolution is one hook, `_grid_mapping_writer(cf_var)`, and one
changed line in the 230-line method. netCDF returns `cf_var.variable`, so its
output is unchanged byte for byte. The base returns an adapter whose
`__setattr__` writes into `cf_var.attributes`. Decided with the user,
2026-10-15.

**F3. `_attribute_handlers` moves to `cf/`, in this pull request.** Spec §12.4
assigns it to PR 6: `cf/saver.py` imports `ATTRIBUTE_HANDLERS` from the netCDF
package, which imports `cf.saver` back, and the cycle survives only because
`_attribute_handlers` imports nothing from `iris.fileformats.cf`. Two source
files and four test files name it. It is private — no deprecation alias is
owed. It is the first task, and its own commit, so that the relocation and the
behaviour work stay separately reviewable. Decided with the user, 2026-10-15.

**F4. `zarr/_encode.py` is a new module the spec's §4.1 layout does not list.**
The write side needs the same kind of pure value conversion the read side has
in `_decode.py`: attributes to JSON-native types, `_FillValue` to its
dtype-dependent encoding, masked arrays to filled ones. Putting them in
`_dataset.py` would push a module that is already 780 lines before any write
code well past the ~1000-line aim in `lib/iris/AGENTS.md`, and would mix pure
functions in with the zarr-python calls, which is what makes `_decode.py`
unit-testable without a store. Decided with the user, 2026-10-15.

**F5. xarray goes in the requirement files now; the lock files are the human
developer's.** Spec §6 puts xarray in with PR 6. PR 4 already regenerates all
three lock files to add `zarr`, so PR 6 regenerating them guarantees a conflict
and a second slow rebuild on rebase. So: `xarray` is added to the test section
of `requirements/py3{12,13,14}.yml` in this pull request, and
`requirements/locks/*.lock` is left alone for the human developer to regenerate
by hand once PR 4 has landed. The consequence to state in the pull-request
body: **until those locks are regenerated, CI has no xarray, so every
cross-reader conformance test skips.** It is installed in `iris-dev` — one
package, exactly as spec §6 measured — so the tests run locally while the work
is being done. Decided with the user, 2026-10-15.

**F6. Every zarr-python and xarray fact the write path leans on reproduces on
today's versions.** Checked against zarr 3.4.1 and xarray 2026.9.0,
2026-10-15:

| Claim | Result |
|---|---|
| `mode="w-"` on an existing store raises | `FileExistsError: Cannot create '' with mode 'w-' because it already contains data. Use mode 'w' to overwrite.` |
| Creating an array over an existing name raises | `zarr.errors.ContainsArrayError: An array exists in store ... at path 'data'.` |
| A non-JSON attribute value poisons the mapping | `TypeError: Object of type float32 is not JSON serializable`, **and** `dict(group.attrs)` afterwards still contains the rejected value |
| A floating `_FillValue` written as a plain JSON number | xarray's open fails for the **whole dataset**: `TypeError: Failed to decode fill_value: expected str or bytes for dtype float32, got float` |
| The same value written as base64 of `struct.pack("<d", ...)` | xarray opens, and masks the filled points |
| An integer `_FillValue` written as a plain JSON integer | xarray opens, and masks the filled points |
| `dtype=str` | a native variable-length `string` array; xarray reads the values back |
| `dtype="<U5"` | a `fixed_length_utf32` array; xarray reads the values back too |
| `shards=` larger than `chunks=` | `Array.shards` and `Array.chunks` both readable back, so the alignment guard has its two numbers |

**F7. `write_handle()` returns the `ZarrDatasetVariable`, not the
`zarr.Array`.** Spec §4.5 says "`ZarrDatasetVariable` returns its
`zarr.Array`"; PR 4 implemented `return self`, with the reason in its
docstring. Returning `self` is the better answer — the wrapper is what applies
the write-side encoding, and `da.store` only needs `__setitem__` — but it
substitutes a new object for the one the spec checked for picklability. So the
picklability the spec verified of `zarr.Array` must be re-verified of
`ZarrDatasetVariable`, under a `pickle.dumps`/`loads` round trip of the whole
delayed graph, which is what a `distributed` scheduler requires. Task 8 does it.

**F8. `_CUBELIST_SAVER_MODULES` is PR 4's, and lists only netCDF.** PR 4 added
the frozenset at `lib/iris/io/__init__.py:36` with one member,
`"iris.fileformats.netcdf.saver"`, replacing the substring test spec §4.7
describes. `iris.fileformats.zarr.saver` joins it here — `save()` takes a
`CubeList` directly, because a Zarr store holds many arrays and is opened once.
Forgetting this does not raise: `iris.save` would loop over the cubes and call
the Zarr saver once per cube, so every cube after the first would meet a store
that `mode="w-"` refuses. Task 9 pins it.

**F9. The `.zarr` suffix reaches `find_saver` already.** PR 4's §4.7 item 3
teaches `iris.io.find_saver` to match `.zarr` with or without a trailing
separator, so `iris.save(cube, "out.zarr/")` works. What is missing is only the
`_savers` entry that maps the suffix to a module — nothing in the dispatch
needs further teaching.
